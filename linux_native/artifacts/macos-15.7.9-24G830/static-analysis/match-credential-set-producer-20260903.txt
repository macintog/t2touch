# Exact 24G830 normal-unlock credential-set producer

Recovered from the full macOS 15.7.9 (24G830) OTA already retained locally.
Apple binaries are deliberately excluded from Git. Exact binaries, x86_64
slices, and disassembly are frozen in the root-owned read-only snapshot
`24G830-match-credential-set-producer-20260903T151500Z`.

## Producer chain

- `-[MechanismTouchId _startMatching]` creates a `BKMatchOperation`, calls
  `externalizedContext` on the mechanism, and passes the result directly to
  `setCredentialSet:` (`0x3ebd` through `0x3ee2`). It then sets the normal
  login purpose to 3 or the unlock purpose to 4; ordinary unlock does not use
  purpose 6.
- `-[BKMatchOperation optionsDictionaryWithError:]` maps purpose 4 to
  `BKOptionMatchForUnlock` and maps `_credentialSet` to
  `BKOptionMatchForCredentialSet`.
- `BiometricKitXPCServer initMatchOperation` converts those options to bit 1
  (`forUnlock`) and bit 8 (`forCredentialSet`). Thus the native `_matchFlags=9`
  observation is ordinary unlock plus a credential set, not a flag-only
  BioLockout bypass.
- `performMatchCommand:` writes a fixed 68-byte command-4 header. In the
  credential-set branch it writes the credential length at offset 8 and
  copies its bytes to offset 12. Length must be below 33. This exactly matches
  the 23P6068 driver's 1..32-byte validation and copy behavior.

The Linux ACM implementation externalizes the live password-authorized policy
1007 context as exactly 16 bytes. The recovered producer proves that those
same external-form bytes are the native credential-set payload. The exact
ordinary unlock header is therefore flags 9 at offset 0, Apple UID 501 at
offset 4, length 16 at offset 8, the live external form at offset 12, and zero
padding to byte 68. The context must remain live until match cleanup finishes.
